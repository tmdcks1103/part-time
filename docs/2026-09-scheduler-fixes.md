# 근무표 오류 분석 및 개선 기록

2026-09-24 로컬 수정 및 검증 결과입니다. 아직 운영에 배포하지 않았습니다. Supabase 재개 후 DB 연결과 실제 웹 API 조회는 확인했으며, 운영 DB에 대한 저장 검증은 아직 수행하지 않았습니다.

## 원인과 수정

| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |

기존 근무 불가 날짜가 이미 잘못 이동된 채 서버에 저장되었다면 원래 월은 자동으로 복원할 수 없습니다. 해당 월의 실제 날짜를 다시 확인해야 합니다. 수정본은 이후 월 이동에서 날짜가 변형되는 것을 막습니다.

## 사용 흐름

- 왼쪽에서 조교 선택 → 월별 근무 불가 / 고정 수업 시간 입력 → 근무표 확인.
- 수업 시간 재입력 후 조교별 확인 완료. 수업이 없는 조교도 확인 필요.
- 근무표의 칸을 선택하면 수동 배정 패널 표시. 설정, 저장 버전, 동료 활동은 접어서 보관.
- 서버 저장 상태를 별도 표시하고 실패 시 재시도 제공. 다른 사용자와 충돌하면 미전송 편집을 자동 폐기하지 않음.
- 모바일 390px에서 가로 넘침 없이 명단, 편집기, 근무표를 순서대로 배치.

## 데이터 호환성

- 새 테이블이나 DDL 변경은 필요하지 않습니다. 기존 `classes` JSONB에 `{version: 1, confirmed, days}`를 저장합니다.
- 옛 수업 시간 JSON은 최초 수정 시 `classes.previous`에 보관합니다. 조회만으로 DB의 원본을 변경하지 않습니다.
- 명단과 초안의 저장 요청은 조회에서 받은 `baseRevision`이 필요합니다. 오래된 요청은 409, revision 없는 요청은 428로 거절하여 덮어쓰기를 막습니다.
- 월/기간별 저장 버전은 사용자가 명시적으로 저장하는 체크포인트입니다. 현재 편집은 별도 초안으로 자동 저장됩니다.
- 로컬 보관은 해당 브라우저에 한정됩니다. 기기 간 공유 완료 여부는 서버 동기화 상태를 기준으로 확인합니다.

## 검증 결과

- 회귀 테스트 19개: 부분 배정, 하루 1회 제한, 여러 달 균형, 말일 보존, 월별 불가 날짜, 주말 수업, 수업 초기화 및 재입력, 빈 명단, 저장 확인 순서, JSONB 키 순서 등.
- 실제 Chromium과 Web Worker로 브라우저 시나리오 14개: 즉시 새로고침, 월 왕복, 입력 중 수업 시간 보관, 빠른 월 전환, 오프라인 복구, 느린 조회/저장, 수동 배정, 삭제/빈 명단, 여러 달에 걸친 기간 배정, 다른 브라우저의 변경 충돌 등.
- 타입 검사와 Next.js production build 통과. 1440px/390px 화면 확인.
- 실제 로컬 API에서 잘못된 본문/범위와 revision 없는 요청의 400/428 응답 확인. 정상 저장의 SQL 실행은 DB 연결 복구 후 추가 확인 필요.
- 브라우저 테스트는 격리된 API 응답을 사용합니다. 따라서 이 결과가 운영 DB 연결 성공을 의미하지는 않습니다.

## 로컬 성능 비교

동일 기기의 6월 예제, 5회 실행 중앙값 기준입니다. 이전 기본 시도 2,500회와 새 기본 500회를 비교했습니다.

| 항목              |  이전 | 수정 후 |
| ----------------- | ----: | ------: |
| 배정 계산 시간    | 372ms |    81ms |
| 조교 간 시간 편차 | 3시간 |   3시간 |
| 미배정            |   1칸 |     1칸 |

기본 계산 시간은 약 78% 감소했습니다. 이는 로컬 계산 측정이며 전체 페이지 로딩 시간이나 운영 서버 성능의 측정치는 아닙니다. 계산 자체도 UI 스레드 밖에서 실행하므로 입력을 막지 않습니다.

조교 1명만 남긴 재현 조건에서는 이전 코드가 244시간을 배정하며 하루 1회 제한을 22건 위반했습니다. 수정본은 118시간을 배정하고 제한 위반은 0건이며 나머지 칸은 미배정으로 남깁니다.

## DB 연결 복구

현재 환경이 가리키는 프로젝트는 `mlipcymflrmurmcvtony`입니다. 초기에는 읽기 전용 쿼리가 `tenant/user ... not found`로 실패했습니다. 사용자가 제공한 Supabase 화면에는 관리자/소유자 계정의 무료 활성 프로젝트 2개 한도로 Resume이 거절되었다고 표시되었습니다.

사용자가 프로젝트를 재개한 뒤 기존 연결 설정을 변경하지 않고 다음을 확인했습니다.

- 실제 DB 조회 성공: 조교 12명.
- `roster_assistants`, `schedule_drafts`, `schedule_versions` 테이블 존재.
- 로컬 앱의 `GET /api/roster`: HTTP 200, 조교 12명, revision 반환.
- `GET /api/drafts?scope=month:2026-06`: HTTP 200, 해당 월의 저장된 초안은 없음.

조회만 수행했으며, 정상 저장과 재조회 흐름의 운영 DB 검증은 남아 있습니다.

무료 프로젝트 한도는 [Supabase 공식 FAQ](https://supabase.com/docs/guides/platform/billing-faq)를 참고합니다. 현재 운영 데이터 변경과 배포는 수행하지 않았습니다.
